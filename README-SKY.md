# Sushi Game: First App Scaffold

This document explains, in sequence, how the existing Sushi Game design and artwork repository became an Expo application, what each new file does, and how to run the result.

> Current status: the project has since been upgraded incrementally to Expo SDK 57. The scaffold account below records the original SDK 55 setup; see section 14 for the upgrade and current iOS Expo Go instructions.

## 1. Reviewed the existing repository

Before implementation, the repository contained:

- `README.md`: the game overview and initial MVP goals.
- `docs/GAME_CONCEPT.md`: the order loop, session state, and planned horror progression.
- `docs/SUSHI_RECIPES.md`: recipe IDs, ingredient lists, and matching rules.
- `docs/ART_ASSETS.md`: artwork requirements and filename conventions.
- `data/sushi.json`: 20 recipe definitions using 12 ingredient IDs.
- `assets/`: background, player, customer, sushi, and ingredient artwork.
- `.github/workflows/require-rc-for-main.yml`: a check requiring pull requests into `main` to come from `rc`.
- An empty `src/` directory.

There was no runnable app or dependency configuration. The existing documentation, recipe data, and GitHub configuration were left intact. No existing content directories were moved or deleted by the scaffold work.

## 2. Established the first-step scope

The selected stack is Expo, React Native, and TypeScript, with React Native Web support. The app runs locally without a backend or account system.

This first version displays:

1. The normal restaurant background.
2. The normal player avatar.
3. One customer image.
4. One random sushi order from the existing JSON catalog.
5. Selectable ingredient buttons with images and labels.
6. Submit Order and Clear buttons.

Basic ingredient validation and new-order selection are implemented. Horror progression and game-over behavior are deliberately deferred.

## 3. Added the Expo project configuration

| Created file | Purpose |
| --- | --- |
| `package.json` | Names the project, declares its dependencies, sets `index.ts` as the entry point, and defines run and verification commands. |
| `package-lock.json` | Records the resolved dependency tree so installations can be reproduced. Generated by npm. |
| `app.json` | Sets the app name, slug, version, portrait orientation, light interface style, iPad support, and Metro web bundler. |
| `tsconfig.json` | Extends Expo's TypeScript configuration, enables strict checking and JSON imports, and disables TypeScript file emission. Allows the test's explicit `.ts` import. |
| `.gitignore` | Excludes dependencies, Expo local state, build output, logs, TypeScript build metadata, and `.DS_Store` files from new Git additions. It does not untrack files already in Git. |

The scaffold uses Expo SDK 55, React 19.2, React Native 0.83, and TypeScript 5.9. Exact installed versions are recorded in the lockfile.

React Native Web and React DOM support the browser version. `react-native-safe-area-context` keeps native content clear of device cutouts and system UI. `@expo/metro-runtime` supplies Expo's web runtime integration.

## 4. Created the application entry point

### `index.ts`

Imports the root component and passes it to Expo's `registerRootComponent`. This is the application entry point for native and web builds.

### `App.tsx`

Wraps the game screen in `SafeAreaProvider`, then renders `GameScreen`. Keeping this root component small leaves room for navigation or other app-wide providers later.

## 5. Created the static asset registry

### `src/assets/registry.ts`

Provides explicit, literal `require(...)` references for every supplied game image, grouped into five exports:

| Export | Keys | Contents |
| --- | --- | --- |
| `backgrounds` | Levels `0` through `5` | Six restaurant backgrounds. |
| `playerAvatars` | Levels `0` through `4` | Five player avatar states. |
| `customers` | `customer_01` through `customer_05` | Five customer sprites. |
| `sushiImages` | Recipe IDs | All 20 completed sushi images. |
| `ingredientImages` | Ingredient IDs | All 12 ingredient images. |

Literal asset references let the bundler discover local image files. Rendering code selects an already-registered image by ID rather than constructing a dynamic `require` path.

During the earlier repository review, rice and nori images were missing and the level-2 background had a double `.png.png` extension. During scaffolding, the two ingredient images and the corrected background filename appeared in the shared workspace. The final registry uses those files; the scaffold did not create that artwork or perform that rename.

All progression artwork is registered for future use, but this screen always renders `backgrounds[0]` and `playerAvatars[0]`.

## 6. Separated game rules from rendering

### `src/game/game.ts`

Contains the game types and pure functions, with no React Native UI imports:

- `ingredientIds`: the 12 supported ingredient IDs.
- `IngredientId`: a TypeScript type derived from that list.
- `Recipe`: the recipe ID, display name, and required ingredients.
- `GameState`: the current order, selected ingredients, and optional feedback text.
- `GameAction`: toggle, clear, and submit actions.
- `randomOrder`: picks a recipe from a supplied catalog and rejects an empty catalog. An injectable random function makes selection testable.
- `matchesRecipe`: compares ingredient sets without depending on selection order. Missing or extra ingredients fail validation.
- `gameReducer`: updates state in response to actions.

Toggling an ingredient adds or removes it. Clear removes all selected ingredients and feedback while retaining the current order. Submit checks the current selection, produces success or mismatch feedback, clears the selection, and replaces the order with the next supplied recipe.

Random selection happens outside the reducer, so the reducer remains deterministic. A new random order can be the same recipe as the previous order.

There are no failure counters, success counters, progression calculations, persistence, or terminal states in this implementation.

## 7. Connected the existing recipe catalog

### `src/game/recipes.ts`

Imports `data/sushi.json` directly and exports typed recipes. It checks each ingredient ID against the supported ingredient list and throws an error for unknown ingredients.

All 20 existing recipes are available for random orders. The JSON is bundled with the application; it is not fetched from a server. This check validates ingredient IDs, not every possible catalog error such as duplicate recipe IDs.

## 8. Built the mobile-first screen

### `src/screens/GameScreen.tsx`

Uses React's `useReducer` with the separate game reducer and initializes the first order randomly.

The screen includes:

- `background_horror_0.png` as a full-screen background.
- `player_frazzled_0.png` as the chef image.
- `customer_01.png` as the fixed customer image.
- The current recipe's name and matching sushi image.
- A three-column grid of ingredient controls.
- Selection highlighting, ingredient labels, and a selected-ingredient count.
- Clear and Submit Order buttons.
- Feedback for the previous submission.

Submit is disabled when nothing is selected. After either a correct or incorrect submission, the next random order appears and the ingredient selection resets. The customer image remains the same.

The layout uses safe-area insets, a vertically scrollable screen, and a centered maximum content width of 520 points. This supports narrow portrait screens while keeping the interface compact on wider browser and tablet displays. On shorter phones, scrolling may be needed to reach the buttons.

Ingredient controls expose accessible button roles and selection states. Feedback uses a polite accessibility live region where supported.

## 9. Added focused game-logic tests

### `src/game/game.test.ts`

Uses Node's built-in test runner to verify:

1. Ingredient matching ignores order and rejects missing or extra ingredients.
2. Random selection can reach both ends of the catalog and rejects an empty catalog.
3. Toggling, clearing, and submitting update state and feedback correctly.

The tests exercise game logic without requiring a simulator or browser. The test command uses Node's TypeScript stripping support; use a recent Node version that supports `--experimental-strip-types`. Setup was verified with Node 26.8.2 and npm 11.19.1.

## 10. Installed dependencies and verified the scaffold

The following checks completed successfully:

```bash
npm run typecheck
npm test
npx expo export --platform all
```

- TypeScript checking passed.
- All three game-logic tests passed.
- Expo produced production bundles for iOS, Android, and web, resolving the registered artwork.
- The development server started and bundled the web application successfully.
- Expo's dependency compatibility check reported that packages were up to date, with an offline-mode reliability notice.

Production exports were generated under ignored `dist/`. Bundling is not the same as installing and testing a native app: physical-device and simulator testing remain outstanding. No automated visual or browser-interaction test was performed.

### Setup issues encountered

- Initial dependency downloads failed because sandbox network access could not resolve npm. Installation proceeded after network approval.
- Expo's dependency installation reported a transient missing CLI module error after installing packages. Subsequent fresh Expo commands, including exports and the compatibility check, worked.
- The sandboxed development-server attempt could not start successfully. A development server started outside the sandbox on port 8082 and bundled web successfully.
- npm emitted transitive dependency deprecation and vulnerability notices during installation. A later offline audit is not a definitive security review, and no blanket dependency upgrade was applied.

## 11. Run the application

From the repository root, install dependencies if needed:

```bash
npm install
```

Start Expo's development server:

```bash
npm start
```

Use the terminal's platform options or run a platform command directly:

| Command | Purpose |
| --- | --- |
| `npm run web` | Starts the browser version. |
| `npm run ios` | Starts Expo and requests the iOS simulator; requires the appropriate macOS/Xcode setup. |
| `npm run android` | Starts Expo and requests an Android emulator or connected device; requires Android tooling. |
| `npm run typecheck` | Checks TypeScript without building files. |
| `npm test` | Runs the three game-logic tests. |
| `npx expo export --platform all` | Creates production JavaScript/assets for all three platforms under `dist/`; does not create store-ready native binaries. |

A compatible Expo Go installation can also open the development project using the QR code shown by `npm start`. The phone must be able to reach the development computer.

If the default port is occupied, accept Expo's alternate-port prompt or specify one:

```bash
npm start -- --port 8082
```

No backend, environment secrets, or database setup is required.

## 14. Incremental upgrade to Expo SDK 57

The upgrade followed Expo's [incremental upgrade guide](https://docs.expo.dev/workflow/upgrading-expo-sdk-walkthrough/) without changing game logic, rendering, assets, or recipe data.

### SDK 55 to SDK 56

Ran these commands in sequence:

```bash
npm install expo@^56.0.0
npx expo install --fix
npx expo-doctor@latest
npm run typecheck
npm test
```

Expo resolved to 56.0.21 and aligned React Native to 0.85.3, React/React DOM to 19.2.3, safe-area-context to 5.7.0, and TypeScript to 6.0.3.

The first typecheck exposed missing Node test types under the upgraded configuration. Adding explicit `react`, `react-native`, and `node` entries to `compilerOptions.types` in `tsconfig.json` fixed it. Typechecking and all three tests then passed.

Doctor passed 21 of 22 checks. The remaining check identified SDK 56's known Hermes V1 regression and recommended SDK 57. The next upgrade step resolved that warning.

### SDK 56 to SDK 57

Ran the same sequence with the next SDK:

```bash
npm install expo@^57.0.0
npx expo install --fix
npx expo-doctor@latest
npm run typecheck
npm test
npx expo export --platform all
```

Final installed versions include Expo 57.0.22, React Native 0.86.3, React/React DOM 19.2.3, Metro runtime 57.0.15, and TypeScript 6.0.3. Expo's resolved public configuration reports `sdkVersion: '57.0.0'`.

- Doctor: all 21 checks passed.
- TypeScript: passed.
- Game-logic tests: all three passed.
- Production exports: iOS, Android, and web passed.

The upgrade changed `package.json`, `package-lock.json`, and `tsconfig.json`, plus this documentation. No game source changes were required. npm reported 10 moderate transitive dependency vulnerabilities; Doctor's successful compatibility checks are not a security audit, and no unrelated forced upgrades were applied.

### Opening in current iOS Expo Go

Expo's [September 3, 2026 announcement](https://expo.dev/changelog/expo-go-57-login) confirms that the App Store version supports SDK 57 and requires the same Expo account in both the CLI and iOS app.

1. Update Expo Go from the iOS App Store.
2. In this repository, run `npx expo login` if you are not already signed in.
3. Sign into the same account in Expo Go on the phone.
4. Stop any development server left running from SDK 55 or 56.
5. Run `npx expo start --go --clear`.
6. Keep the phone and development computer on a reachable network and scan the QR code with the iPhone camera.

The dependency checks and iOS bundle verify SDK compatibility, but an actual device launch has not been verified here: this environment has no available `simctl` tooling or accessible iPhone. The final on-device check is to open the app, confirm the normal background/avatar and ingredient controls, and try Clear and Submit.
